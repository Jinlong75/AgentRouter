# 阶段收尾：文档核对与更新这份清单

## 一、文档核对表（按项目实际增删）

每个阶段收尾逐项问一句"这个阶段的改动让它过时了吗"，核对结果写进进度记录。

开发中每次行为或工作方式变化，先检查直接受影响的文档与技能；阶段末再用下表查漏。每项记录为“已核对无需改”“已更新（文件/提交）”“待更新（原因/负责者）”或“不适用（原因）”，不能只写一句“文档已同步”。可把互不重叠的核对项并行分配，最后由主导统一核对版本、术语和命令的一致性。

| 位置 | 什么时候要改 |
|---|---|
| 用户指南、README（功能列表、截图、快速开始、当前版本） | 用户可见的行为、界面、命令变了；每次发布前。每一步写明在软件里做还是只能在终端里做 |
| 随软件分发的技能、项目模板、角色文档 | 派发、等待、验收等流程或命令变了；角色职责、任务说明写法变了 |
| 帮助文字、命令用法、关于页、首次引导、空状态 | 功能变化让原来的说法不再成立 |
| 协议文档（命令、字段、事件、文件格式） | 随任务合入当场写 |
| 演示数据 | 界面或状态有了新形态，演示要能看到 |
| 第三方许可说明 | 新增或升级依赖、字体、图标 |
| 写死在检查里的数量、顺序、文字 | 加了标签页、状态、菜单项，改了文案 |
| 安装器的说明与清单 | 安装内容、技能清单、路径变了 |
| 公开仓库的导出清单 | 新增了要公开或不该公开的文件 |
| 版本号 | 发布时 |

## 二、从进度记录提取经验

每个阶段收尾，读这个阶段进度记录里的"主导的失误""教训""偶发失败"几节，逐条判断：

1. **能不能交给机器**：能写成检查脚本、核心里的拦截或默认值的，列成任务，做完后不再进清单。
2. **是不是通用的**：换一个项目也会发生的，进这份清单；只和本项目的工具、平台、目录有关的，写进本项目的主导角色文档。
3. **够不够分量**：同类问题出现过 2 次以上，或者只出现一次但造成了大量返工，才收录。
4. **写成一行**：放进 SKILL.md 对应的时刻，原因和例子写进 examples.md 的同名一节，去掉项目细节。

清单控制在约 40 条以内：加新条目时，看看有没有已被机器检查取代、或很久没再发生的旧条目可以删。改动随阶段的合并请求一起交用户审阅。
