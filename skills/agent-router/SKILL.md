# 派发工作给执行者

**什么时候派出去**：要求能写得比实现短、结果能用命令客观验收的工作（实现、补测试、按清单改文档、只读调研）派出去；需要审美、方向或取舍判断的自己做，或先写清判断再派。

**先确认**：当前目录是 git 仓库并且有 `.agent-router/project.json`（没有就先按 `lead-workflow` 的初始化做，问过用户再做）；`node "<技能目录>/core/ar.mjs" agents list` 里有可用的执行者（没有就请用户在 AgentRouter 软件的 Agent 页导入）。

本技能只管**怎么派、怎么看进度、怎么收结果**，不规定执行者是什么角色。执行者是用户在 AgentRouter 里导入的 Agent（Codex、DeepSeek、Xiaomi MiMo、Claude、Qoder、自定义命令行等），下文的"执行者"指被派到的那一个。角色默认这样定：没写 `--role` 时，**任何派发**（任务说明或直接写任务文字）都默认带角色：项目里有 `docs/roles/worker.md` 就按执行者角色派（任务说明 `type: review` 时用 `docs/roles/reviewer.md` 当审查者），对应的角色文档不存在就不提角色。要别的角色就写 `--role`，明确不要角色写 `--role none`（例如和项目分工无关的一次性小事）。

派发一律写 `dispatch` 子命令：第一个参数是单个小写英文词（例如把 list 打成了 lsit）又不是文件时，核心不派发、退出码 2，提示改用 `ar dispatch "<词>"`。

下文的 `<技能目录>` 指本文件所在目录的绝对路径，派发入口是其中的 `core/ar.mjs`（AgentRouter 核心）。

## 用法

```
node "<技能目录>/core/ar.mjs" dispatch <任务说明文件 | "任务文字"> ["补充说明"] [选项]
```

- 脚本以**当前工作目录**作为仓库根目录，运行前先切到仓库根目录。执行者只在 git 仓库里运行；当前目录不是仓库时，先问用户工作放在哪个项目目录。
- 第一个参数是存在的文件 → 当作任务说明，让执行者完成其中全部内容并验证、提交、汇报；否则当作直接给执行者的任务文字。
- 仓库根目录有 `AGENTS.md` 时，总是让执行者先读它。

| 选项 | 作用 |
|---|---|
| `--profile <执行者>` | 本次任务用哪个执行者（`node "<技能目录>/core/ar.mjs" agents list` 查看；`roles` 子命令看谁能当执行者、谁能当审查者）。不给就按路由决定：任务说明的 `worker` 写了具体执行者就用它 → 项目规则 → 全局规则（按任务类型）→ 预设默认规则（调研、杂务先比同币种最低单价（输入 + 输出），其余的按预设建议类型；全局 `routing.implicit` 关掉时跳过）→ 兜底 → 默认执行者；想先看会派给谁，运行 `route --spec <任务说明> --explain`（只计算，不派发）。`node "<技能目录>/core/ar.mjs" route config` 列出"预设默认规则"，`node "<技能目录>/core/ar.mjs" agents list` 和 `node "<技能目录>/core/ar.mjs" route suggest` 里的"擅长 / 避免"看各执行者适合什么 |
| `--role <角色>` | 开头告诉执行者"你在本项目中的角色是「xxx」"，并让它读 `docs/roles/<角色>.md`。也可以直接给角色文档路径。不给时按上面的默认角色。`--role none` 明确不提角色 |
| `--name <记录名>` | 记录文件名。任务说明默认用文件名，任务文字默认 `task-<时间>` |
| `--sandbox <沙箱>` | 本次任务的沙箱。只读的调研、排查类工作用 `read-only` |
| `--no-worktree` | 项目开了 worktree 模式时，这一次仍在主工作区里做（见"worktree 模式与验收"） |
| `--base <分支>` | 只用于 worktree 模式的任务：这一次从 `<分支>` 开出 worktree，门禁、"合并主分支后重跑"、批准合并、撤销都以它为准，不改项目配置（例如在阶段分支上开发时 `--base stage/xx`）。批准前主工作区要切到这个分支；基线与项目配置的 `baseBranch` 相同时，合并后可用 `accept --push` 推送，`--no-push` 禁止推送，不指定时按 `push.afterAccept` 配置；基线不同时跳过自动推送，需要时用 `ar push` 单独推 |
| `--model` / `--effort` / `--tier` | 本次任务的模型、推理强度、服务档位。一般不传，用用户的默认值；单次任务确实需要再传。按任务难度定强度时，更推荐写进任务说明的 frontmatter（`effort: high`、`model: …`）：派发时自动带上，`ar status` 会注明"来自任务说明"。任务说明或路由规则给出的强度超出支持范围时，派发会被拒绝并列出可选值；命令行显式给出的强度不做这项范围校验，使用前仍须核实实际支持值。命令行的值优先于任务说明 |

**不确定参数对不对**时，先在前台加环境变量 `AR_DRY_RUN=1` 跑一次：只打印实际记录名和将发给执行者的指令，不运行、不写任何文件。

记录都在仓库的 `.agent-runs/<记录名>/` 下：`report.md` 是最终汇报，`progress.log` 是精简进度，`raw.log` 是执行者的原始输出。实际记录名以脚本开头打印的为准（重名时会自动加序号）。

### 默认配置

模型、推理强度等默认值是**每个执行者各自的**，由用户在软件"Agent → 编辑"里设置，命令行是 `agents update <名> --model <模型> --effort <强度>`（`agents list` 查看）；全局设置用 `config` 查看。派发时只为这一次任务决定参数，不要改用户的默认配置。

`agents update --effort` 在预设提供了可选值、但所填强度不在其中时只提示，仍保存原值；保存成功不代表该模型支持这个强度，须按实际能力选择。

脚本输出或进度里出现 `配置：未找到 config.json…` 时，任务照常执行；向用户汇报时顺带说一句可以在软件里导入执行者、设置默认的模型和推理强度。用户说不用设，就运行 `config init`，以后不再提示。出现 `配置：config.json 无法读取…` 时，把原因转告用户。

## 步骤

1. **准备任务**。需要运行诊断命令时，先核实任务类型与适配器工具权限：`research` / `review` 会强制只读，不能靠 `--sandbox workspace-write` 覆盖。较大的工作写成任务说明文件：目标、范围、允许改动的文件、不做什么、验收标准、汇报要回答的问题；先读取目标项目配置的 `specRequired`，按其中要求写字段和章节。新项目模板默认要求代码类（`type` 为 `code` / `fix` / `test` / `refactor`）有 `## 受影响的已有测试` 一节；项目可以另加要求（例如本项目还要求 `## 换环境` 和指定字段），派发前检查，缺了会被拒绝；写说明时用 `node "<技能目录>/core/ar.mjs" spec impact <说明>` 列出可能受影响的已有测试与界面检查，合入后用 `node "<技能目录>/core/ar.mjs" spec impact <说明> --docs` 核对文档；一次一个。小的一次性工作可以直接给任务文字。
2. **任务说明先提交**（只 `git add` 具体文件），让执行者从干净的基线开始。确认 `.agent-runs/` 在 `.gitignore` 里，不在就提醒用户或按项目约定加上（`node "<技能目录>/core/ar.mjs" init` 会生成项目约定并加上它）。派发前核心会自动检查这份说明（和 `node "<技能目录>/core/ar.mjs" spec check <说明>` 同一套检查）：依赖不存在或成环、frontmatter 值里有没加引号的 ` #`、当前分支与项目基线不同又没写 `--base`、全量独占验收时限不足，都会拒绝；`core/` 和 `app/src/main/shots*.ts` 一起改只警告"建议拆成核心与界面两份"。想先看：`node "<技能目录>/core/ar.mjs" spec check <说明> --json`。
<!-- host:dispatch -->
3. **后台派发**：用 Bash 工具，设 `run_in_background: true`，命令先切到仓库根目录再运行脚本，例如：
   ```bash
   cd "<仓库根目录>" && node "<技能目录>/core/ar.mjs" dispatch docs/specs/012-xxx.md --role worker
   ```
   派出后读一下这条后台命令的输出，拿到实际记录名。
<!-- /host:dispatch -->
4. **告诉用户**任务已派出、记录名是什么、在哪里看进度：开着监控软件就在软件里看；否则 Windows 上会弹出标题为"<执行者显示名> <记录名>（只看）"的窗口，也可以运行 `<技能目录>/core/ar-watch.cmd` 手动打开。进度最后出现"=== <执行者显示名> 结束：exit=0 …"就是这一次尝试做完了（门禁、自动重试、交叉审查可能还在后面，以 `ar wait` 的结果为准）。给粗略的用时预期（小改动约 5 分钟，中等任务 10～30 分钟，大块工作可能一小时以上），不做精确承诺。派发失败时（输出里有"出错："），把原因和解决办法告诉用户，由用户决定接下来怎么做。
<!-- host:wait -->
5. **并行**：依赖已满足、改动范围不重叠的任务一起派；每次有任务结束，先运行 `node "<技能目录>/core/ar.mjs" next` 看空闲名额、待验收（含冲突）的任务与可以派发的说明（默认只列最近 14 天提交过的说明，旧说明用 `ar next --all`），`next --dispatch` 派满，再验收（`wait` 结束时有可派的说明也会提示）。**等待时**不要编辑执行者可能在改的文件，避免它 `git add` 时把你的半成品一起提交。可以做不冲突的事。后台命令结束时你会自动收到通知，**不要用 sleep 循环轮询**；用户问进度时用 Read 读 `progress.log` 的末尾几十行。
   派发用了 `--detach`、或任务是托管的（派发命令马上返回）时，**等结果用 `node "<技能目录>/core/ar.mjs" wait <记录名>`**，同样设 `run_in_background: true`：任务进入待验收、失败或停止时它会自己退出，你收到一条通知。同时等几个任务就各跑一条。**不要自己写循环脚本或长期挂着的监视去盯任务**：会话里起的后台循环在你忘了它之后还会一直跑，越积越多，拖慢整台机器，还会让门禁里的测试偶发失败、被误当成环境问题。
<!-- /host:wait -->
6. **验收**（`ar wait` 结束后）。退出码：0 = 待验收或完成，1 = 执行者失败或被停止（用 `status` 区分），2 = 派发错误，3 = 门禁未通过（自动重试后仍失败），4 = 等待超时（只用于 `wait --timeout`，任务仍在进行，再等一次）。按这个顺序读，**不重复门禁已经跑过的命令**，只抽查：
   1. `node "<技能目录>/core/ar.mjs" status <记录名> --json`：状态、尝试次数、门禁与审查摘要、汇报里推断清单与 `TODO(lead)` 的条数；
   2. `.agent-runs/<记录名>/gate.json`（见"失败与重试"）；
   3. 有审查时 `review show <记录名>`，逐条 `review confirm`（见"worktree 模式与验收"）；
   4. `.agent-runs/<记录名>/report.md`：推断清单里涉及取舍的逐条确认，`TODO(lead)`、偏离说明、已知问题、"需要越界"逐条处理或转告用户；改了测试或界面检查时还要看 `## 断言改写`，逐个列出受影响的文件（门禁会查）；
   5. `diff <记录名>`（不用 worktree 的项目看 `git show --stat` 与关键 diff），特别看被删掉的行。
   6. 合入若干任务后看全量验收提醒：`accept` 与 `next` 会提示自上次通过的全量验收以来已合入多少任务，还没有通过的全量验收时提示"还没有通过的全量验收，已合入 n 个任务"；达到项目配置 `fullVerifyEvery`（默认 5）时会提示建议现在跑一次全量验收，就在主分支跑 `node "<技能目录>/core/ar.mjs" verify --detach`，用 `node "<技能目录>/core/ar.mjs" verify --last` 看上次结果与之后合入数；合入数从最近一次**通过**的全量验收起算，`--last` 显示的是最近一次结果（可能是失败），两者的起点不同。结果对应一个提交，验收期间分支或提交变了那次作废。全量验收跑项目配置的 `fullVerify`（没配就跑 `verify`）；合入主分支或发布前用 `node "<技能目录>/core/ar.mjs" verify --require` 只读确认当前提交已通过。
7. **决定**：满意就 `accept <记录名>`（`--ack "<说明>"` 只用于确认汇报里的"已知问题""需要越界"等小节；门禁或审查结果缺失、过期，审查意见没逐条标记，要先补齐（重跑门禁、`review confirm`），确需覆盖才用 `accept <记录名> --force --reason "<原因>"`，要用户批准）；小问题 `retry <记录名> --note "具体要改什么"`；worktree 任务里你补了小修、门禁未通过或门禁阶段被停止，就 `retry <记录名> --regate --note "改了什么"`（不用 worktree 的任务不能用）；方向不对 `reject <记录名> --reason "原因"` 后改写说明重新派发；冲突 `retry <记录名> --rebase`。细节见下面两节。
8. **向用户汇报**用用户的语言、说白话：做了什么、门禁和审查结果、发现的问题、下一步、需要用户决定的事。

到了写说明、派发、验收、收尾这些时刻，环境里有 `lead-practices` 技能就按它对应的一节自查。不装 Claude Code 技能的主导（Codex 等）按项目里 `docs/roles/lead.md` 的同一套流程工作。

## 失败与重试

- **门禁**：用任务说明派发、并且写了验收命令、限定了允许改动的文件或要求提交时（任务说明与项目配置 `.agent-router/project.json` 合起来看），启用门禁；非 worktree 模式下派发前要求说明已提交、工作区干净，worktree 模式下说明须在所选基线中，主工作区不要求干净。直接写的非只读文字任务使用 worktree 时，门禁取项目配置的允许范围和验收命令，不要求提交。执行者结束后核心按门禁配置检查范围、提交和验收命令，结果写在 `.agent-runs/<记录名>/gate.json`。退出码 `3` 表示门禁未通过；执行者自己也可能以 3 退出，以 `gate.json` 为准。门禁还会比较 `base..HEAD` 里的测试文件：删除测试、断言净减少、超时数值变大时提示"测试检查可能被削弱"，要求汇报的 `## 断言改写` 逐个说明受影响的路径；明细在 `gate.json` 的 `testWeakening`。
- **额度用完、被限流、服务连不上**：算"环境"原因，不计重试次数、不扣执行者的分，核心按路由换下一个可用的执行者接着做（你明确指定了执行者、手动重试、直接写任务文字的任务不换人）；`route config` 里能看到谁被限流到几点。
- **自动重试**：门禁未通过或执行者异常退出时，核心在同一工作区自动再试一次，并把失败原因和失败命令的输出末尾附在指令后面。次数上限取任务说明的 `max_retries`（没写就取项目配置的 `maxRetries`），默认 2，也就是最多共 3 次。执行者没能启动、任务被停止时不重试；直接写任务文字派发的任务也不自动重试。等待期间什么都不用做，`ar wait` 会等到最后一次尝试结束。
- **每次尝试单独保存**在 `.agent-runs/<记录名>/attempts/<n>/`：`prompt.md` 是这次实际发出的指令，另有这次的 `raw.log`、`report.md`、`gate.json`。顶层 `gate.json` 是最近一次门禁结果；`report.md` 是最近一次产生的执行者汇报。只重跑门禁的尝试不启动执行者，审查时会使用最近一次执行者汇报并注明来源。`progress.log` 跨尝试连续写，第 2 次起有一行 `=== 第 n 次尝试（…）===`。
- **手动重试**：自动重试用完仍然失败，或者结果不满意但方向没变时，用第 3 步同样的后台方式在仓库根目录运行：
  ```bash
  node "<技能目录>/core/ar.mjs" retry <记录名> --note "补充说明"
  ```
  它在同一工作区接着做一次，`--note` 作为"主导补充说明"附在指令后面；任务已经完成时必须给 `--note`。`--profile <执行者>` 换执行者。任务还在进行时会被拒绝，先停止。要保留前几次的失败信息就用 `retry`，不要重新 `dispatch`（那会新开一个记录）。
  **跨配置重试的模型/强度**：`retry --profile` 换到另一执行者配置时，原命令行、任务说明、路由中的 `model` / `effort` / `tier` 都不继承，改用新配置自己的值；只改任务说明不能指定这次跨配置重试的参数。派发前核对目标配置，启动后用 `ar status` 的生效值与来源核验；需要固定参数时使用已获授权的专用配置，不擅改用户默认。配置名没变时，任务说明层会重新读取。
  普通 `retry` 沿用原始指令与只读模式，不自动把主分支的新说明正文复制进旧 worktree；改 `type`、`read_only` 或 `--sandbox` 不会把已有只读记录变成可执行命令的记录。需要改变模式时，先核实当前授权，再用 `redispatch` 或明确的新派发重新计算模式，保留旧现场并合并核算同任务派发次数。`--note` 要写完整补充要求，或明确给出已提交的版本与读取命令（`git show <提交号>:docs/specs/<文件>`）；不要只说“读最新说明”。门禁参数重新读取，不等于任务目录里的正文已更新。
- **自动重试都没通过**：核心默认按"同样强度 → 提高推理强度 → 最后一次换强执行者（`ar route strong set <名>` 设了才换）"重试；都失败时状态里有"自动重试都没通过，建议主导接手"，这时你读汇报和门禁结果，自己判断是改任务说明重派、手动 `retry --note`，还是接手。
- **执行者写了"## 需要越界"**：说明它需要改允许范围以外的文件，核心不再自动重试，等你决定。同意就优先用 `node "<技能目录>/core/ar.mjs" scope approve <记录名> [--paths …] [--dry-run] [--detach]`：它把汇报里申请的路径加进任务说明、提交并重试（只批准其中几处就写 `--paths`，先用 `--dry-run` 看会改什么）。手工处理时就自己把这些路径加进任务说明的 `allowed_paths` 并提交（不用 worktree 的项目还要把任务说明文件本身也加进去，否则你的这次提交会被门禁当作越界），再 `retry`——`retry` 会重新读已提交的任务说明，没提交会被拒绝。不同意就改写任务说明重新派发，或放弃。worktree 模式的任务没有"任务说明文件本身也要列进去"这一条（任务说明改在主分支上，不进任务分支）。

## worktree 模式与验收

项目配置 `.agent-router/project.json` 写了 `"worktree": true` 时，符合条件的任务在**各自的 worktree 和分支**（`ar/<记录名>`）里执行，不动主工作区，可以同时进行多个（超过并发上限就排队）。任务说明的 `chore` 默认不使用 worktree；说明显式写 `review: true` 或 `worktree: true` 时可使用。直接写的非只读任务文字也使用 worktree，包括 `chore`；只读文字任务不用。`--no-worktree` 可关闭本次 worktree。

- **改动范围重叠也会排队**：先派发、还在排队 / 准备 / 运行 / 门禁中的任务，和后派发的任务的 `allowed_paths` 有重叠时，后派发的等前一个离开这几种状态（进入待验收也算）再开始，基线换成那时主分支的最新提交。任务说明**不写 `allowed_paths` 就按整个仓库算**，和谁都重叠，所以想并行就给每份任务说明写清楚、互不重叠的范围。手动 `retry` 也查重叠：重叠时会排队等对方离开运行 / 门禁。和**待验收**的任务重叠不排队，但进度里会提示"合并后可能冲突"；`ar overlaps` 列出互相重叠的待验收任务和建议的批准顺序（先派发的先批准），批准其中一个后，其余的会自动按新基线重跑门禁，冲突的进"冲突"。项目配置 `exclusiveCommands` 的命令按完全相等或前缀匹配。门禁按验收命令里**第一条**匹配的命令决定：它与配置项完全相等时，门禁独占，期间不开始新任务或其他门禁；只按前缀匹配时只阻挡其他门禁，新任务仍可开始。例如配置 `npm run shots` 时，`npm run shots -- --focus <名>` 属于后一种。

- **派发前**：任务说明要先提交到本次所选基线分支，执行者才看得到；未指定 `--base` 时使用项目配置的 `baseBranch`。主工作区不要求干净。worktree 建好后先跑项目配置的准备命令（`setup`，例如 `npm ci`）。
- **交叉审查**：任务说明写 `review: true` 时，门禁通过后会按审查者配置安排只读审查，结果在 `review.json`（`ar review show <记录名>`，或 `ar status` 里的"审查：…"）。是否允许执行者本人、同模型家族参与由审查者规则决定；结果中的 `crossed` 仅表示审查者与执行者使用不同的 Agent 配置，不保证家族不同。默认只是建议，不打回。验收时**先读审查问题**，逐条用 `ar review confirm <记录名> <编号> valid|invalid --note "…"` 标出你的判断（成立的，要么让执行者修，要么在驳回 / 重试的说明里写明）；这些标记用来算审查者的准确率。
- **门禁通过 = 待验收，不是完成**：`ar wait` 这时返回 0，并多打印一行"待验收：…"。改动还在任务分支里，没有进主分支。
- **验收**（在仓库根目录、主分支上运行）：
  - 先看改动：`node "<技能目录>/core/ar.mjs" diff <记录名>`；
  - 合并：`accept <记录名>`（`--no-ff` 一个任务一个合并提交，合并后删除 worktree 与分支）；撤销已合并的任务用 `revert <记录名>`（只追加一个反向提交，冲突时什么都不改）；
  - 不要：`reject <记录名> --reason "原因"`（`--keep-branch` 保留分支）。
  - `accept` 被拒（退出码 2）时什么都没改，按提示处理（例如先 `git switch <主分支>`、先提交主工作区的改动）。提交主工作区的改动用 `projects commit <项目路径> --message "说明" --files <文件…>`，只提交列出的文件；先 `projects changes <项目路径>` 看有哪些，**不要** `git add -A` / `git add .`。
- **合并冲突**（`accept` 退出码 4）：主分支已恢复原样。用 `retry <记录名> --rebase` 在 worktree 里合并主分支：没冲突就只重跑门禁，有冲突就派执行者解决，之后回到待验收，再 `accept`。
- **落后于主分支导致门禁失败**（主分支上已经修好的问题、或分支里手动合并过主分支后门禁把别的任务的文件算成越界）：同样用 `retry <记录名> --rebase`，它也能用在门禁失败、已中断的 worktree 任务上。不要让执行者自己 `git merge` 主分支——门禁仍按最初的基线比较。
- **准备命令失败**：修好项目配置里的 `setup` 后 `retry <记录名>`，会先重跑准备命令。
- **查看状态**不等待：`status <记录名>`。清理已合并、已驳回后没删掉的 worktree 和过期的执行者会话记录：先 `gc --dry-run` 看清单，告诉用户，用户同意再 `gc`。
- **评分**：任务结束后 `report <记录名>` 给执行者与主导各一个 0～100 的分数和每项明细；有交叉审查的任务多一组"审查者"（改了文件、没按格式给结论、被你标为不成立的问题会扣分）。门禁失败是任务说明写错或漏写造成的，用 `report <记录名> --blame <第几次>=spec` 归到主导；和谁都无关的（机器过载导致的计时失败、用户自己在任务运行时装软件触发的工作区外写入）用 `=environment`。

## 推送与拉取

- **只用核心推送**：`node "<技能目录>/core/ar.mjs" push <项目路径> --by lead`（先 `--dry-run` 看领先 / 落后几个提交）；拉取用 `pull <项目路径> --by lead`（只快进）。核心只推主分支、只做普通推送，不推标签、不强制推送。
- **项目没有开启"允许主导推送"（`push.allowLead`）时，核心会拒绝你的推送和拉取。这时不要绕过核心直接 `git push` / `git pull`**，告诉用户：需要的话在软件"项目 → 编辑配置 → 推送"里打开，或者他自己在软件里点"推送"。
- 文件先在本地仓库创建并提交，再推送；合并请求合入后，把本地主分支更新到合并结果，让用户在本地目录就能看到。
- 推送被拒（远程有本机没有的提交）、或两边分叉时，不要自己合并或 rebase 远程的提交，把情况告诉用户。
- 没有凭据时核心不弹登录窗口、直接失败，让用户在终端里手动 `git push` 一次完成登录。

## 已知坑

<!-- host:interrupt -->
- **关闭主导会话可能连带中断未托管的执行者**。需要关掉会话也不中断时使用托管；回来先查原记录，仍在运行就用`ar wait`接回，不重新派发。确已中断、需要恢复执行时按"手动重试"在原记录上`retry`，补充说明核对已有未提交改动，保留失败证据；不能因为主导换了会话就创建重复任务。
<!-- /host:interrupt -->
- **要停止任务**，在仓库根目录运行 `node "<技能目录>/core/ar.mjs" stop <记录名>`，托管和没托管都一样。不要直接结束进程，也不要只停后台命令：那样执行者可能还在跑。
- 托管的任务（脚本输出会说明）由监控软件启动，关掉会话不会中断。会话关掉后再回来，用第 3 步同样的后台方式在仓库根目录运行 `node "<技能目录>/core/ar.mjs" wait <记录名>`：任务还在跑就接着等，已经结束就立刻返回结果。
- **会话里不要把 `node "<技能目录>/core/ar.mjs" wait` 用 `&` 挂到后台**：安装器注册的 Claude Code PreToolUse 钩子会拒绝这种命令，原因原文是"不要在会话命令里用 & 把 ar wait 挂到后台：会随会话结束被停掉，也容易堆积。改用工具自带的后台运行（Bash 的 run_in_background）执行 ar wait <记录名> --timeout <秒>，或在前台运行。"改用 Bash 的 `run_in_background` 跑 `node "<技能目录>/core/ar.mjs" wait <记录名> --timeout <秒>`，或在前台跑；要交给 AgentRouter 托管、关掉会话也不中断，派发或重试时加 `--detach`（`node "<技能目录>/core/ar.mjs" dispatch … --detach`、`node "<技能目录>/core/ar.mjs" retry <记录名> --detach`）。
- **严格模式拒绝**：项目开了 `leadStrict` 时，`dispatch`、`redispatch`、`retry`、`accept`、`reject`、`next --dispatch` 会报"严格模式：主导还没确认当前版本的交接文件与经验清单（<原因>）。先运行 ar lead brief，读完后按最后一行运行 ar lead ack <确认码>"。先运行 `node "<技能目录>/core/ar.mjs" lead brief`、按最后一行运行 `node "<技能目录>/core/ar.mjs" lead ack <确认码>` 再重试；软件发起的（`--host agentrouter`）、带 `--by human` 的 `accept` / `reject`、`AR_DRY_RUN=1` 和只读命令不受限。
- 同一任务不要同时跑两份：记录名会自动错开，但两个执行者会抢同一个工作区。重新派发前先确认旧任务已经结束（看监控软件，或看进度文件末尾有没有结束行；Windows 上也可以查进程：`Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match 'ar\.mjs' }`）。
- 进度里突然出现大量没整理过的原始文本，多半是执行者程序升级改了输出格式，原始输出都在 `raw.log` 里，把现象告诉用户。
- Windows PowerShell 5 的 `Set-Content -Encoding UTF8` 和 `Out-File` 会写 BOM；给执行者准备的文件用编辑工具写。
