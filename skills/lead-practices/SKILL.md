# 主导经验清单

到了下面某个时刻，把那一节过一遍。每条一行；要看原因和例子，读 [references/examples.md](references/examples.md) 里同名的一节。标"（软件已检查）"的，AgentRouter 会自己拦住，知道就行。

**同一个错误第二次出现时，先想办法让软件或检查脚本拦住它，再考虑往这里加一条。**

**并行是默认做法，不是等用户提醒才做的事**：开工时、以及每次有任务结束（`ar wait` 返回）时，运行 `ar next` 看空出的名额、机器余量、待验收（含冲突）的任务和依赖已满足、改动范围不重叠的说明，`ar next --dispatch` 派满，再去验收或写下一份说明；说明里用 `depends` 写依赖。（软件已检查：`ar wait` 结束时有可派的说明会提示）

## 1. 写任务说明时

- 写到参数、字段、文案键、每条检查要断言的效果这一级；说明里含糊的地方，执行者会自己做决定。
- 先全文搜索依赖旧行为的测试和界面检查（含写死的文案、顺序、数量，以及命令用法与帮助文字——错误提示里的用法行常被逐字核对），把**完整**结果贴进说明的"受影响的已有测试"，据此写允许改动的范围；搜索结果不接 `head` / `tail` 截断。新规则和已有测试矛盾时，写明改哪条、为什么。
- 写"可以在哪里做到"之前先读那段代码，不凭印象写；诊断先核实任务类型、工具权限与材料可读范围，不能只给执行者一个跨工作区绝对路径；重试可更新哪些字段也按当前实现确认。
- 要解析自由文本（汇报、日志、标题）的任务，说明里先贴出所有真实写法的样例（含编号、加粗、冒号、下级标题），并优先复用已有解析器；否则审查会一轮轮找出新写法，返工四五次。
- 方案依赖外部工具的某个能力（沙箱参数、命令行开关）时，写说明前先做一次最小的真实实验确认它真的生效；帮助文本写着支持不等于在你的平台上有效。
- 说明里要求"复用 / 共用 / 抽出"某个已有函数，或要接到某个已有入口时，先找到它所在的文件并列进允许范围；漏列时执行者会按规矩停下，白跑一轮。
- 同时要改主进程（或核心）、界面和界面检查的任务，执行者常常只做一小部分就停下：按"主进程 / 核心"与"界面 + 检查"拆成两份，前者先合入。
- 一份说明只做一件可验收的事，比 1～3 小时大的先拆；写明"做不通就停下汇报，不改清单以外的文件"；门禁时限按验收命令估，要跑全量界面检查的按全量用时的两倍写。
- 要用主分支或其他任务的新内容：先核实依赖修复确已进入所选基线；派发时指定基准（`ar dispatch --base`），冲突用 `ar retry --rebase`，不让执行者手动合并。

## 2. 派发与并行时

- 每到一个节点（用户反馈、任务合入、等门禁）先按依赖与改动范围列出待办：无依赖且范围不重叠的开发、文档与只读核对一起派，改同一批文件的串行。原定"以后再修"的小项，赶上反正要重跑的完整回归时一并修入。（软件已检查：范围重叠的自动排队）
- 长时间独占的验证（完整界面检查、打包）理想上只挡住会争抢资源的验证，不挡执行者写代码；当前完整独占会暂停新任务，聚焦独占只挡其他门禁，新任务仍可开始。（软件已检查）
- 查代码、读日志、整理证据也派给执行者做只读调研，主导只读结论，不用主导自己的子代理；耗时的阅读按独立文件组拆成小批，每批写明读取范围、独立报告位置与时间预算。
- 并发上限按可用内存、CPU 负载、任务依赖和改动范围定，不只看核数；派发前、任务结束后短采样，出现资源争用证据先减并发并记录，不挂长期监视循环。全量回归、完整界面检查和打包按项目规则独占。（软件已检查：自动档按内存估算并发）
- 执行者只跑和改动相关的测试，全量验收只由门禁跑。两边都跑全量，是机器过载最常见的原因。
- 并行合入多个任务时，每合入几个就在集成分支上单独跑一次全量检查，早点发现过时的旧检查。

## 3. 等待与后台进程

- 等任务用 `ar wait <记录名>`，不写循环脚本，不长时间挂着监视；长任务可以用 `ar dispatch --detach` 在独立后台进程中启动；它不属于软件托管，关闭会话仍可能中断任务。回来先查原记录，仍在运行时用 `ar wait` 接回，不重新派发。
- 重试补充要自包含，或给出说明的确切提交号与读取命令；旧工作区未必有主分支的最新正文，不能只说"看最新说明"。
- 适配器识别到最终结果事件后，若汇报已就绪、进程持续无输出且没有运行中的子进程，软件会兜底结束未退出的执行者；按结果事件判定成功或失败，并记一笔。
- 主导自己跑的长验证、打包脚本用脱离会话的独立进程启动，再一次性等待；挂在会话里的后台命令会随会话结束被停掉。判断或结束进程按"进程号 + 启动时间"，只看进程号可能误伤别的进程。
- 阶段收尾确认没有遗留的执行者、门禁命令、浏览器和自己起的后台命令；清理前先 `ar gc --dry-run` 核对范围，未完成任务和用户要求保留的历史工作区不清理。

## 4. 验收时

- 以当前待合并代码对应的门禁、审查和验收产物为准，不以执行者自述为准；变更使哪些证据失效就补查哪些，没有新变化不重复同一验证。
- 读 diff 里**被删掉的行**（删掉一条检查、一个分支，自述里通常不会提）和新增的中文字符串（某些终端里写中文会丢编码，变成一串问号）。
- 核对新增断言的鉴别力：检查重画后的新元素，覆盖非默认状态；必要时用一次受控反向实验确认目标逻辑失效会红，并恢复原文件。（软件已检查：说明或汇报 `## 反向实验` 一节里按 JSON 写的实验由门禁自动改坏、运行、恢复，`mutations_required` 规定至少几条；只写文字的不执行）
- 汇报里的"已知问题""需要越界"逐条处理；只在单独运行时通过、没在完整流程里通过的不算通过。
- 改写旧断言要逐条记"原 → 新 → 原因"；不按测试名开例外；放宽检查先问用户。
- 截图按文件名逐张核对"应该看到的东西在不在"，不只看有没有报错。
- 审查意见逐条判断，不整体接受也不整体忽略：看实际触发条件，区分本次引入与既有性质，理论上可能但实际不会发生的判不成立并写明理由。派发、门禁、审查次数分开记，按整条链路耗时找瓶颈，不把格式失败算成实现失败。
- 判断做完没有，看功能是否进了所开发的项目本身（代码、默认配置与模板、安装或部署流程），在一台新机器、一个新项目里默认可用；只在本机环境、本机配置或个人目录里生效的不算做完。需要使用者记得去做的步骤，优先由项目里的程序在对应时刻检查或提醒，不只写在文档里。
- 执行者自测因沙箱限制失败（构建工具读不到上级目录、写不了版本库）标"环境"，由门禁在沙箱外确认，不让执行者绕过。

## 5. 门禁失败、偶发失败时

- 先保存现场（日志、截图、门禁输出），重跑前把上一次的失败产物复制走，再在约定的时间内排查；不靠重跑变绿。
- 先怀疑测试读取的时机（读得太早或太晚、滚动没到位、动画没结束），改成等事件，而不只是加长超时。
- 不删断言、不放宽超时来让它通过；定位到原因再改。
- 环境造成的失败（额度用完、限流、网络、磁盘、系统负载）单独标"环境"，不算执行者的失败；换执行者或等待，不改任务说明。
- 检查命令不接管道（`| tail`、`| head`），要截取输出时先保存退出码；把"改文件 → 跑测试 → 提交"串成一条命令时，用退出码判断前一步成功后再提交。

## 6. 交给用户走查前

- 每一轮走查新建一份文档，旧文档标"已停止更新"并链到新的。新文档只写这一轮要做的事：开头一张表列出要做的几件事、在哪做、多久；然后按顺序逐步写（点哪个按钮、输入什么、应该看到的原文）；末尾放结果表。
- 准备命令写成一整段能复制的脚本，检查不通过就只打印醒目的提示、不往下执行；不要依赖 `throw` 中断后面粘贴的命令（交互式终端会继续跑后面的行）。能让用户自己核实的结果给出可复制的命令和预期输出。
- 每一步写明在哪个环境做（演示数据还是正式安装的软件），并考虑用户环境和开发环境的差异：没有全局 git 身份、演示里的执行者是假的、默认配置和开发配置不同。
- 主导先按授权自己核对步骤和预期，能自动验证的先自动验证；只把需要人判断的留给用户（审美、手感、真实账号），不把某一种桌面工具当作唯一验收方式。

## 7. 隔离与密钥

- 符合条件的任务使用独立 worktree，其他任务可能使用主工作区；执行者用户目录按执行者配置隔离，并非每个任务独立，适配器可能保留真实配置目录（如 Codex 的 `CODEX_HOME`）。工作区之外的写入要报出来。
- 不自己读密钥再传给子进程，也不写进命令行、日志、报告；由软件按配置注入。
- 提交前先 `git add`，再跑仓库的提交前检查（隐私路径、内部名词、控制字符）；检查不过不提交。
- 门禁运行期间不手动启动执行者的命令行工具，免得和门禁抢配置与缓存。

## 8. 随阶段更新文档

- 维护一张"功能变了要跟着改的地方"清单（模板见 [references/closeout.md](references/closeout.md)）；合入改了行为的任务时，对它的说明跑 `ar spec impact <说明> --docs`，逐条核对列出的文档；协议、命令、字段的变化随任务合入当场写，同次核对受影响的技能、模板、角色指令与用户指南，阶段收尾再逐项核对一遍。
- 决定要编号记录；自己做的决定标"待确认"，写明怎么回退；编号撞了，后来的顺延。
- 阶段收尾从进度记录的"失误""教训"里提取新条目，更新这份清单（规则同见 closeout.md）。
- 没有任务碰过的文档也会过时：阶段收尾和发布前，派执行者只读核对全部文档（README、用户指南、协议、角色、模板、技能及其参考）与当前代码、命令帮助是否一致，产出过时清单（位置、证据、建议），再按清单派同步任务；主导只读清单。
- 很少用到的内容（超过两个阶段没有任务、命令或用户问到）在核对清单里标出来，经用户同意移到 `archive/`，不直接删；被引用的先改引用。

## 9. 暂离、收尾与发布

- 进入暂离模式先确认截止时间和目标；每个任务开始前看时间；截止前停止开新任务，写报告：做了什么、自己做了哪些决定、哪些需要人工走查。
- 出发布候选：先收齐审查与文档/技能核对并完成必要修改，再独占回归、打包和公开同步；后续改动逐项判断哪些证据失效，只补受影响步骤，同时保留项目必做的完整回归，核对产物哈希与最终标签差异。合入主分支、出候选前用 `ar verify --require` 确认当前提交已通过全量验收（只读，不通过时逐条列原因）。
- 同步到公开仓库前跑内容扫描（个人信息、本机路径、内部文档名）。
- 推送、合并到主分支、打标签、发布，先征得用户同意。

## 10. 控制成本与选模型

- 按任务难度给每份说明选执行者、模型和推理强度：机械改动、文档同步、按清单补测试用便宜模型和低强度；跨模块逻辑、并发与安全相关、反复返工的用强模型和高强度；写进说明的 `model` / `effort`，不改用户的默认配置。
- 主导自己也分档：写说明、判断审查意见、架构取舍用强模型；出候选、打包、跑既定脚本这类机械步骤可以换便宜模型。需要换时告诉用户，不自己改宿主设置。
- 主导只读结论：长日志、截图核对、审查意见初筛、全文阅读交给执行者先读并写一页摘要，主导读摘要和关键行；不用主导自己的子代理做调研。
- 少汇报中间进度：只在需要用户决定、或到了里程碑时汇报；等待期间不重复读同一份输出。
- 会话越长每一轮越贵：到一个完整的任务边界就把状态写进交接文件，建议用户换新会话。交接文件覆盖改写、保持约 80 行（开工必做、授权与边界、在跑任务与下一步），历史移到归档文件，不追加流水账。
- 用统计看花费：给执行者填单价，按"执行者 × 任务类型 × 强度"看一次通过率与每个合并任务的花费，再调整分工；便宜模型返工多到总花费更高时就换。

## 11. 用自己的工具时

- 用 AgentRouter 开发时遇到的绕路（手改配置、代提交、手动补步骤）当场记成问题并派任务修，不长期绕路；修好后把对应的绕路说明从文档里删掉。
- 加速、省钱、提质量的做法随时补进这份清单；只适用于本仓库的写进角色文档，不写进这里。
