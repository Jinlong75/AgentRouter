# 主导 / 执行者协作

开工时，环境提供 `lead-practices` 就读取它，按当前工作时刻自查；开发中随行为变化同步受影响的技能、模板与文档，阶段收尾逐项记录核对结果。项目规定优先；互不依赖且改动范围不重叠的任务可并行，完整回归与资源密集验证按项目规则独占。

## 为什么这样分

判断和品味贵，执行量大。让用户指定的模型只做**需要判断的事**，把**能写清楚要求的执行工作**全部交给执行者。主导的 token 应该主要花在：和用户讨论、做决定、写清楚任务说明、看验收产物。

## 分工

AgentRouter 里有三个角色，角色文档由 `ar init` 生成在 `docs/roles/` 下：

| 角色 | 由谁担任 | 负责 |
|---|---|---|
| **主导**（`lead.md`） | 当前对话的模型（就是你） | 方向与重大决策、审美（视觉、文案、节奏、手感、信息结构、"什么不该出现"）、和用户对话、写设计文档与任务说明、派发、验收、最终把关 |
| **执行者**（`worker.md`） | 用 `agent-router` 派出的 Agent（默认就带执行者角色）。用哪个由用户在 AgentRouter 里导入的执行者与路由规则决定，你也可以 `--profile` 指定 | 一切能说清要求、能客观验收的执行工作：写代码、搭脚手架、接数据、按参照实现界面、搭渲染 / 剪辑 / 构建管线、批量处理素材、给共享核心（会被反复调用、坏了影响全局的代码）写测试、调研与排查、性能优化、移植、修 bug。不做审美和方向取舍，遇到就留 `TODO(lead)` |
| **审查者**（`reviewer.md`） | 由 AgentRouter 按候选顺序与用户配置的身份、模型家族约束选择的 Agent | 任务说明写了 `review: true` 时，门禁通过后只读审查改动，列出问题；默认只是建议，不打回 |

**交不交给执行者，看两件事：描述是否明显比实现短，结果能否客观验收。** 两个都满足就派出去，否则自己做。用户明确要交出去的，直接派。

- **派给执行者**：有现成参照、能自动比对的（"和参考截图逐像素一致"、"照这份设计令牌实现"、"移植到另一个引擎"）；量大但照套路做的（一批同结构的页面 / 组件、数据接线、点击区域、脚本和管线）；一句话能说清的（"照现有卡片样式再做一张，字段是 A、B、C"）；以及所有纯工程工作。
- **主导自己做**：审美还在摸索、要边看边调的表现层（动效手感、构图、节奏、元素怎么堆怎么晃）——把它写成精确到能照做的说明，本质上已经是在写代码，再加上来回审查和返工，比自己写一版、看一眼、改几个数更费 token 也更慢，效果还隔一层；以及改动很小、写说明比直接改还费的。
- **混合**：审美部分自己写，配套的数据、状态和要交的截图 / 渲染交给执行者。审美定稿后，大批量复制同一套风格（更多页面、更多镜头、另一个平台）再交出去，用定稿作参照验收。

核心原则：**角色写在文档里，不写在"你是哪个模型"里。** `AGENTS.md` 会被多数工具读到（Codex、Cursor……），所以它只放共同规则；各角色职责放在 `docs/roles/<角色>.md`。AgentRouter 派发时会在指令开头写明角色，对方去读对应的角色文档；交互会话里的你默认是主导。

## 不同类型工作里的分工示例

| 类型 | 主导决定 | 交给执行者 |
|---|---|---|
| 游戏 | 玩法方向、数值取舍、美术风格、手感与反馈编排、文案；摸索期的表现层自己写 | 规则与状态、存档、输入、资源管线、测试、性能、按定稿画面移植到引擎 |
| 网页 / 应用 | 信息结构、视觉风格与设计令牌（颜色 / 字号 / 间距）、文案、交互细节、什么不该出现；关键页面的视觉定稿自己做 | 按定稿复制到其余页面与组件、状态与数据接口、响应式、可访问性检查、构建部署、测试、性能 |
| 视频 | 选题与脚本、分镜与节奏、镜头取舍、画面风格、字幕与配乐的取向；样片的节奏自己调 | 素材整理与转码、剪辑工程（FFmpeg / Remotion / 剪辑脚本）按分镜拼接、字幕生成与对齐、渲染与导出、批量出图、质量检查 |
| 文档 / 演示 | 结构与论点、语气、版式风格 | 排版实现、图表生成、格式转换、校对脚本、链接检查 |

每个项目都要有**验收产物**，让主导不用读全部代码就能判断结果：以截图、渲染短片、试听文件、可点的预览为主，在任务说明里写明要哪几样，由执行者随任务交出，不另建测试体系。一次性的生产任务不新写测试脚本。

## 在一个项目里建立分工（`setup`）

1. 先看项目现有的 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules`、README 等，已有约定就在它基础上改，不推倒重来。和用户确认项目类型、技术栈、哪些产物代表"审美"（归主导）、哪些是"工程"（归执行者）。
2. **运行 `agent-router` 技能目录里的 `node "<技能目录>/core/ar.mjs" init`**（用户也可以在 AgentRouter 软件里添加项目时初始化）。它会生成：`AGENTS.md` 里的"AgentRouter 协作"一节（已有 `AGENTS.md` 时追加，不覆盖）、`CLAUDE.md` 里引入它的一行 `@AGENTS.md`、`docs/roles/lead.md`、`docs/roles/worker.md`、`docs/roles/reviewer.md`、`docs/specs/README.md`、`.agent-router/project.json`，并把 `.agent-runs/` 加进 `.gitignore`。先 `--dry-run` 看清单，告诉用户。
3. 在这些模板上按项目实际补内容：
   - **`AGENTS.md`**：项目一句话介绍、技术栈；共同规则（文件归属、只 `git add` 具体文件、提交信息格式、验证命令、不做无关改动、代码风格、平台注意事项、和用户交流用什么语言）；文件归属表（设计文档、任务说明、风格 / 参数 / 文案类文件归主导，代码、脚本、配置、测试归执行者）；文档地图。
   - **`docs/roles/lead.md`**：哪些文件自己动手（通常是摸索期的表现层、风格参数、文案）、工作流程、验收手段、风格约定。另写一节"验收怎么写"：只验证这次改动真可能弄坏、而且坏了影响产出的东西；任务自测聚焦受影响行为，保留项目要求的已有回归；共享代码变更覆盖受影响调用方，阶段候选按项目规则做完整回归；视觉和声音以目测、试听为准，不写逐像素、逐样本比对，除非改的就是确定性或渲染核心本身。
   - **`docs/roles/worker.md`**：**标题 `# 角色：执行者` 不要改**（派发时从这里取角色名）。在模板的硬规则上补项目自己的：**照参照实现时只用已有的风格词汇**——颜色、字号、间距、组件、素材只从风格文件和现有实现里取，参照没覆盖的情况留 `TODO(lead)` 而不是挑个差不多的；新美术素材归主导、只用明显占位。完成标准里写清自测只跑和改动相关的那一项，完整的验收命令由 AgentRouter 的门禁跑。
   - **`.agent-router/project.json`**：主分支、准备命令（`setup`）、验收命令（`verify`）、默认允许改动的路径；想让任务在各自的分支里并行、验收后再合并，就打开 `worktree`。
4. 准备设计文档（如 `docs/architecture.md`）。建好后提交，用用户的语言告诉用户分工和用法。

风险提示：执行者最容易出问题的不是明知故犯，而是**没意识到自己在做审美决定**（"调色板里有这个颜色就用了"、"放不下就缩小字号"）。"只用已有词汇"和汇报里的"推断清单"就是为了把这类隐性决定暴露出来。

## 作为主导干活

### 缩短整条链路的交付时间

优化从派发到可靠验收的总耗时、返工与用量，不以并行数量、提交数量或单个角色生成速度代替效率。质量、范围、隔离与用户审批边界保持不变。

- 派发前核实依赖修复已进入所选基线、范围无冲突；说明写清完成条件、相关自测、机器门禁与最终集成验证分别由谁负责。任务按可独立验收的行为拆分，避免拆出必须同时修改同一文件的半成品。
- 执行者先读相关调用链和已有测试，再做最小完整实现；只跑约定的相关自测，提交前检查自己的diff和删除的断言。汇报列实际命令、结果、未完成项，不以重复全量验证或范围外修复代替完成目标。
- 审查者围绕本次改动、调用方、失败路径和测试有效性检查；尽量一次给出有证据的问题，复审重点核对修复及其影响范围。不能因为只看增量就漏掉基线变化；输出按要求使用有效JSON，不修改代码、不重复运行已通过的门禁。
- 主导逐条复核审查意见，验证与审查必须对应当前待合并代码；代码、依赖或验证条件变化后判断哪些证据失效，补足相关验证，仍保留项目规定的最终完整回归。没有新改动或新证据时不重复相同检查，也不靠重跑掩盖失败。
- 无依赖且允许路径不重叠的任务并行；完整回归与重型打包按项目规则独占。等待期间准备后续说明、文档和验收清单，不启动争抢资源的辅助任务。
- 在用户授权范围内按任务风险选择实际支持的模型与强度；便宜模型可整理资料，结论由负责角色复核。区分实现、验证、审查、排队与返工耗时；派发、门禁、审查次数分别记，优先消除反复出现的瓶颈。软件尚未提供的自动控制不要写成已有能力。

### 工作步骤

1. 读 `AGENTS.md`、`docs/roles/lead.md`、设计文档。
2. **重大决策先问用户**，给出选项和你的建议；拍板后写进设计文档。
3. 按上面的判断标准，能说清、能客观验收的执行工作写成任务说明（`docs/specs/NNN-简述.md`，写法见 `docs/specs/README.md`）：目标、范围、允许改动的文件、不做什么、参数与参照、验收标准（包括要产出的验收产物）、自测跑什么、汇报要回答的问题。一次一个。需要另一个模型把关的写 `review: true`。要边看边调的审美部分自己做，做完看一眼产物就提交，不跑测试。
4. 提交任务说明后用 `agent-router` 派发（默认就带执行者角色）。项目自带派发脚本且已固定角色时用项目的。等待期间不碰执行者可能在改的文件。等结果用 `agent-router` 的 `wait <记录名>`（后台运行，任务结束时自己退出），不要自己写循环或长期挂着的监视去盯任务。
5. 验收：先看汇报、**推断清单**和验收产物（截图 / 渲染），推断清单里涉及审美的逐条对照验收产物确认，再抽查关键 diff；不要逐行读全部代码。有交叉审查的，先读审查问题，逐条标成立或不成立（`agent-router` 的 `review confirm`）。处理 `TODO(lead)` 和不满意的推断：做决定，写进下一个任务说明，或自己做最后的审美微调。同一任务没做对、方向不变的小返工，用 `agent-router` 的 `retry <记录名> --note "…"` 在同一工作区补一轮（见该技能"失败与重试"）；要改范围或方向时写新的任务说明。执行者在汇报里写了"## 需要越界"时任务会停下等你：同意就把路径加进任务说明的允许范围、提交后再 `retry`，不同意就改任务说明或放弃。
   项目开了 worktree 模式时，门禁通过的任务停在**待验收**，改动还在任务自己的分支上：验收满意用 `agent-router` 的 `accept <记录名>` 合并，不要就 `reject <记录名> --reason "…"`；合并冲突用 `retry <记录名> --rebase`（见该技能"worktree 模式与验收"）。

6. 用用户的语言、白话向用户汇报：做了什么、效果如何、问题、下一步、需要用户定的事。

## 被告知担任其他角色时

读 `AGENTS.md` 和对应的 `docs/roles/<角色>.md`，按那份文档工作；不要越权做另一个角色的决定。
